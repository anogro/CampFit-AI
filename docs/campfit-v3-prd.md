# CampFit AI v3 제품 요구사항 문서

- 문서 상태: Draft for approval
- 기준일: 2026-07-12
- 대상 버전: CampFit AI v3 MVP
- 제품 범위: 부모동반 해외 교육 경험 AI 상담
- 구현 상태: 본 문서는 요구사항 정의이며 구현을 승인하지 않는다.

## 0. 문서의 기준과 결정 우선순위

이 문서는 다음 순서로 해석한다.

1. `CAMPFIT-V3-PRD-AND-ARCHITECTURE` 요청에서 확정한 결정
2. `CampFit AI 서비스 기획서.hwpx`
3. `CampFit AI v3 점수 매트릭스.hwpx`
4. 5개 와이어프레임 상태: 시작, 기본정보 입력, AI 상담, 로딩, 결과
5. 2026-07-12 기준 현재 코드와 Supabase의 읽기 전용 감사 결과
6. 과거 v1·v2 문서는 참고 자료

자료 사이에 충돌이 있으면 위 순서가 앞선 자료를 따른다. 특히 다음 사항은 최신 결정으로 고정한다.

- MVP 상담 모델은 Upstage Solar다. Gemini는 런타임 대체 모델이 아니다.
- 화면 상태는 시작, 기본정보, 상담, 로딩, 결과의 5개지만 실제 페이지 route는 3개다.
- 전체 상담 원문은 서버에 보존한다. 다음 Solar 호출에는 현재 발화와 구조화된 상태를 보내며, 이전 원문 전체를 매번 다시 보내지 않는다.
- v2의 긴 설문, 10개 프로그램 유형, 8개 가족 성향, 품질평가 점수는 v3 MVP로 가져오지 않는다.
- 내부 적합도와 운영 품질은 별개다. 운영 품질 공개 점수나 인증은 MVP 범위가 아니다.

## 1. 제품 정의

CampFit AI v3는 만 5~12세 아이와 같은 도시에 머무는 부모·보호자가 1~4주의 해외 교육 경험을 검토할 때, 복잡한 조건을 대화로 정리하고 현재 데이터에서 살펴볼 경험 방향, 도시, 프로그램을 제시하는 AI 상담 서비스다.

추천의 단위는 한 가지 성향이나 단일 프로그램이 아니다.

```text
추천 경험 방향
× 아이에게 맞는 참여 형식
× 필요한 지원
× 가족에게 현실적인 도시
× 현재 조건에서 살펴볼 프로그램
```

제품은 예약 대행이나 합격·운영 품질 보증 서비스가 아니다. 결과의 기본 표현은 “AI 최종 추천”이 아니라 “현재 조건에서 살펴볼 후보”다.

## 2. 문제와 목표

### 2.1 해결할 문제

부모는 프로그램 이름을 검색하기 전부터 다음 문제를 겪는다.

- 아이에게 학교 경험, 영어 집중, 프로젝트, 문화 활동 중 무엇이 맞는지 알기 어렵다.
- 아이의 영어 수준과 낮 시간 분리 가능성이 실제 참여 형식과 어떻게 연결되는지 판단하기 어렵다.
- 한국어 지원, 부모 연락, 응급 대응을 하나의 “관리 여부”로 뭉뚱그리기 쉽다.
- 프로그램 비용과 항공·숙박·생활비를 포함한 가족 전체 예산을 혼동하기 쉽다.
- 아이에게 좋은 프로그램이 가족이 머물기 좋은 도시인지 별도로 비교하기 어렵다.
- 가격, 일정, 지원이 확인되지 않은 경우에도 검색 결과가 확정 사실처럼 보일 수 있다.

### 2.2 MVP 목표

- 명확한 조건이면 4~5회, 일반적으로 5~8회, 최대 10회의 AI 질문으로 필수정보를 정리한다.
- 아이와 부모의 주체, 명시 사실과 추론, 필수와 선호를 분리한다.
- 하드 조건을 통과한 DB 후보만 사용한다.
- 경험 방향 1~2개, 역할이 다른 도시 최대 3곳, 프로그램 최대 2~3개를 설명한다.
- 미확인 데이터는 적합·부적합으로 단정하지 않고 확인사항으로 이동한다.
- 모든 추천을 입력 근거, DB 근거, 알고리즘 버전으로 재현할 수 있게 설계한다.

### 2.3 성공 지표

초기 베타의 핵심 지표는 다음과 같다.

- 기본정보 입력 완료율
- 상담 시작 대비 정상 결과 도달률
- 정상 상담의 질문 수 중앙값 5~8회
- 필수정보가 모두 확인됐을 때 불필요한 추가 질문 비율 0%
- 아이·부모 주체 혼동 0건
- 명시 답변을 추론이 덮어쓴 사례 0건
- DB에 없는 도시·프로그램·가격·지원 생성 0건
- 결과에서 프로그램 카드 또는 도시 카드를 1개 이상 여는 비율
- “확인 필요” 항목 확인 후 상담·문의로 이어지는 비율
- 다시 하기와 답변 수정 후 정상 회복률

예약·결제 전환율은 MVP 성공 기준이 아니다.

## 3. 타깃 사용자와 전제

### 3.1 핵심 타깃

- 아이 나이: 출발 시점 만 5~12세
- 동행 형태: 부모 또는 법적 보호자가 같은 도시에 체류
- 아이 활동: 낮 동안 데이 프로그램 또는 단기 스쿨링
- 기간: 약 1~4주
- 이용자: 프로그램을 처음 비교하거나 조건을 좁히지 못한 한국어 사용자

### 3.2 핵심 시나리오

1. 첫 해외 교육 경험을 안전하게 시작하고 싶은 가족
2. 국제학교 분위기를 경험하되 정규수업 부담은 조정하고 싶은 가족
3. 영어 성과보다 문화·활동 속 영어 노출을 원하는 가족
4. STEM·예술·스포츠 같은 관심 분야 프로젝트를 원하는 가족
5. 아이가 프로그램에 참여하는 동안 휴식, 관광, 어학, 원격근무를 원하는 부모
6. 한국어 비상 지원이나 부모 연락을 필수조건으로 보는 가족

### 3.3 MVP 불변조건

- 이동 인원에는 부모·보호자가 1명 이상 포함돼야 한다.
- 보호자는 프로그램 기간 동안 아이와 같은 도시에 머물 수 있어야 한다.
- 기숙형이나 아이 단독 홈스테이를 일반 후보로 제안하지 않는다.
- 조건이 범위를 벗어나면 억지 추천 대신 서비스 범위 안내와 상담 종료를 제공한다.

## 5. 사용자 여정과 페이지 구조

### 5.1 페이지 route는 3개

| 페이지 | 제안 route | 포함 상태 |
|---|---|---|
| Page 1 시작 | `/campfit/v3` | 시작 화면 |
| Page 2 상담 | `/campfit/v3/consult` | 02-A 기본정보, 02-B AI 상담, 로딩·재시도 |
| Page 3 결과 | `/campfit/v3/result` | 결과, 확인사항, 다시 하기 |

세션 식별자는 URL query에 노출하지 않고 서버가 관리하는 불투명한 세션 쿠키로 연결하는 것을 기본안으로 한다. 실제 route 생성은 별도 구현 승인 후 진행한다.

### 5.2 정상 흐름

```text
시작 CTA
→ 기본정보 5개 입력 및 검증
→ 상담 세션 생성
→ Solar가 현재 발화에서 facts/corrections/conflicts 추출
→ 서버가 사실을 병합하고 진척도·다음 질문 결정
→ 4~8회 내 필수정보 확인
→ 코드가 하드 필터와 점수 계산
→ Solar가 허용된 후보와 근거만 설명
→ 결과 페이지
```

별도의 중간 요약 페이지는 없다. 상담창 안에 “현재까지 확인한 내용”을 접을 수 있는 영역으로 제공한다.

### 5.3 범위 밖 흐름

부모 미동행, 아이 나이 범위 초과, 4주 초과 장기 유학 중심, 기숙형만 희망하는 경우에는 다음과 같이 안내한다.

> 지금 버전은 부모님이 같은 도시에 머무는 1~4주 낮 프로그램을 중심으로 안내해요. 입력하신 조건은 현재 상담 범위를 벗어나 정확한 후보를 제안하기 어렵습니다.

범위 밖 조건을 몰래 완화하지 않는다.

## 6. 상담 입력과 필수정보

### 6.1 기본정보 카드에서 받는 5개 슬롯

| 슬롯 키 | 입력 | 정상 완료 조건 | 비고 |
|---|---|---|---|
| `child_age_at_start` | 출발 시점 만 나이 | 5~12의 정수 | 형제자매가 함께 참여하면 각 아이를 분리해야 하며 MVP는 대표 아동 1명 기준 여부를 확인한다. |
| `departure_window` | 연·월, 방학 또는 기간 범위 | 최소한 운영 시기와 겹침을 판정할 수 있는 범위 | “모름”은 답변 저장은 가능하나 완료로 보지 않는다. |
| `duration_weeks` | 1~4주 범위 | 최소·최대가 유효하고 교집합이 존재 | 선호값과 조정 가능한 최대값을 분리한다. |
| `total_family_budget_krw` | 가족 전체 총예산 | 항공·숙박·생활·프로그램 포함 원화 범위 | 항공 별도 예산은 총예산으로 변환되기 전 완료가 아니다. |
| `travelers` | 아이·부모·형제자매 수 | 참여 아동 1명 이상, 부모·보호자 1명 이상 | “보호자가 같은 도시에 체류” 확인을 이 슬롯의 검증에 포함한다. |

### 6.2 대화에서 확인할 6개 필수 슬롯

| 슬롯 키 | 확인할 내용 | 유효한 명시적 ‘없음’ |
|---|---|---|
| `child_english` | 아이의 이해·대화 수준 | 없음. 수준을 선택해야 한다. |
| `primary_experience` | 가장 원하는 경험과 보조 목표 | 없음. 최소 1개 목표가 필요하다. |
| `region_preference` | 지역, 강도, 양보 가능성 | `no_preference`는 완료다. |
| `required_support` | 아동 직접 지원, 부모 소통, 응급·운영 지원의 `must/strong/soft/none` | 세 축 모두 `none`일 수 있다. |
| `parent_stay_purpose` | 휴식, 카페·식당, 관광, 자연, 어학, 원격근무, 중요하지 않음 | `not_important`는 완료다. |
| `special_care` | 알레르기, 식사, 복약, 건강·감각·생활 지원 | 사용자가 명시한 `none`은 완료다. |

### 6.3 설명을 풍부하게 하지만 완료를 막지 않는 정보

- 가장 걱정되는 점
- 피하고 싶은 경험
- 낮 시간 분리·초기 적응
- 사회 참여·활동량
- 부모 영어 소통 가능성
- 조건별 양보 가능성
- 기대하는 변화

단, 이 정보가 새로운 안전조건이나 하드 조건을 드러내면 해당 사실은 필수 확인 대상으로 승격된다.

### 6.4 질문 방식

- 자연어 메시지
- 한 개 빠른 선택
- 복수 선택
- 숫자·날짜 직접 입력
- “직접 입력” 보조 필드
- 기존 답변 수정

빠른 선택은 AI가 추론한 값을 확인시키는 용도로도 쓸 수 있다. 추론을 사용자가 선택하면 출처가 `explicit_user_statement` 또는 `structured_input`으로 승격된다.

## 7. 진척도와 상담 종료 조건

### 7.1 정확한 진척도 산식

필수 슬롯 수 `N`은 11이다. 각 슬롯의 유효 완료값 `credit_i`를 다음처럼 계산한다.

```text
구조화 입력이며 검증 통과                         credit = 1.0
사용자가 명시한 자연어 답변이며 근거가 있음        credit = 1.0
AI 추론, confidence >= 0.85, 모순 없음             credit = 0.5
AI 추론, confidence < 0.85                          credit = 0
unresolved, conflict, validation 실패, 값 없음       credit = 0

progressPercent = round(100 × Σ credit_i / 11)
```

예:

- 5개 기본정보 완료: `round(100 × 5/11) = 45%`
- 기본 5개 + 상담 3개 명시 + 상담 1개 고신뢰 추론: `77%`
- 10개 명시 + 1개 고신뢰 추론: `95%`
- 11개 명시·확인: `100%`

`0.5`는 UI 진척에는 반영하지만 완료로 간주하지 않는다. 100%는 모든 슬롯이 `1.0`이고 필수 슬롯 충돌이 없을 때만 가능하다.

### 7.2 정상 완료 조건

서버의 `readyForRecommendation`은 다음을 모두 만족할 때만 `true`다.

1. 필수 11개 슬롯이 모두 `1.0`
2. 부모·보호자가 같은 도시에 머무는 MVP 조건 확인
3. 안전, 특별관리, `must` 지원에 unresolved·conflict 없음
4. 경험 방향을 최소 1개 계산할 수 있음
5. 하드 필터와 추천 엔진을 실행할 수 있는 날짜·기간·예산 범위 확보
6. DB에 유효 도시 후보가 최소 2개 있거나, 1개뿐이라는 제한 결과를 명시적으로 만들 수 있음

AI가 `readyForRecommendation: true`를 반환하더라도 서버가 위 조건을 다시 계산한다. 서버 판단이 우선한다.

### 7.3 상담 횟수

- 상담 횟수는 기본정보 카드가 아니라 AI가 사용자에게 보낸 질문 메시지 수다.
- 조건이 명확하면 4~5회, 일반적으로 5~8회, 최대 10회다.
- 여러 필수값이 자연스럽게 연결되면 한 메시지에서 함께 묻되, 사용자가 답하기 어려운 긴 설문으로 만들지 않는다.
- 이미 `1.0`으로 확인된 슬롯은 다시 묻지 않는다.

### 7.4 최대 10회 예외

10번째 질문 이후 추가 질문을 보내지 않는다.

- 안전한 하드 조건이 모두 확인됐고 지역 또는 부모 목적 같은 비안전 슬롯만 남으면 제한적 결과를 생성한다.
- 예산, 특별관리, 필수 지원, 부모동반처럼 안전·현실성에 직접 영향을 주는 값이 없으면 경험 방향까지만 보여주고 도시·프로그램은 “추가 확인 후 제공”으로 보류한다.
- `readyForRecommendation`은 `false`로 유지하고 결과에 누락 필드와 영향 범위를 표시한다.

## 8. AI 역할과 질의·응답 메커니즘

### 8.1 Solar가 담당하는 일

- 현재 발화와 구조화된 대화 맥락 이해
- 아이, 부모, 형제자매, 프로그램의 주체 분리
- 한 문장에서 여러 사실 추출
- 명시 사실, 사용자 수정, 추론 분리
- 목표 강도와 회피 조건 추출
- 부족한 정보와 충돌 탐지
- 다음 질문 후보 제안
- 코드가 제공한 상위 DB 후보의 의미 비교
- 코드와 DB가 제공한 근거를 이용한 결과 설명

### 8.2 Solar가 하지 않는 일

- DB에 없는 도시·프로그램 생성
- 가격, 일정, 연령, 지원, 후기 생성
- 명시 답변을 추론으로 덮어쓰기
- 하드 필터 실패 후보 복구
- 운영 품질이나 안전을 보증
- 전체 후보의 점수를 직접 계산
- 5점 초과 점수 차이를 임의로 뒤집기

### 8.3 호출 컨텍스트

서버는 모든 원문과 수정 이력을 저장한다. 각 후속 Solar 호출에는 다음 최소 컨텍스트만 전달한다.

```text
현재 사용자 발화
현재 활성 구조화 프로필
필수 슬롯별 상태와 출처
관련 evidence 발췌
unresolved와 conflicts
이미 물은 question keys
허용된 next question keys
결과 설명 단계라면 allowlist된 DB 후보와 근거
```

이 방식은 최신 프롬프트의 “원문을 보존하되 구조화 요약을 다음 호출에 전달” 결정을 따른다. 전체 원문은 감사·수정·재현에는 쓰지만 기본적으로 매 호출에 재전송하지 않는다.

### 8.4 구조화 응답 계약

```ts
type SolarConsultationResponse = {
  assistantMessage: string
  facts: Array<{
    key: string
    subject: "child" | "parent" | "family" | "program"
    value: unknown
    source:
      | "structured_input"
      | "explicit_user_statement"
      | "user_correction"
      | "model_inference"
    confidence: number // 0..1
    evidence: string | null
  }>
  corrections: Array<{
    key: string
    previousValue: unknown
    newValue: unknown
    evidence: string
  }>
  unresolved: Array<{
    key: string
    reason: string
    candidateSubjects?: string[]
  }>
  conflicts: Array<{
    key: string
    factKeys: string[]
    severity: "high" | "medium" | "low"
    reason: string
  }>
  nextAction: "ask" | "recommend"
  nextQuestionKey: string | null
  readyForRecommendation: boolean
}
```

검증 규칙:

- 중요한 fact는 evidence가 없으면 활성값으로 병합하지 않는다.
- `explicit_user_statement`와 `user_correction`은 confidence가 1이어야 한다.
- `model_inference`는 명시 fact를 수정할 수 없다.
- child와 parent의 영어·지원·목표를 같은 key로 합치지 않는다.
- `nextQuestionKey`는 서버가 제공한 allowlist에 있어야 한다.
- JSON schema 검증 실패 시 사용자에게 AI 문장을 먼저 노출하지 않는다.
- 서버가 병합·완료·중복질문·추천 가능 여부를 다시 계산한다.

### 8.5 사실 병합 우선순위

```text
최신 사용자 수정
> 최신 명시 자연어
> 검증된 구조화 입력
> 이전 명시값
> confidence >= 0.85 추론
> 낮은 confidence 추론
```

구조화 입력과 명시 자연어가 충돌하면 자동으로 덮어쓰지 않고 수정 확인을 요청한다. 사용자 수정이 확정되면 이전값은 비활성화하되 감사 이력에서 삭제하지 않는다.

### 8.6 다음 질문 선택

서버가 질문 후보별 영향도를 계산하고 Solar는 자연스러운 문장을 작성한다.

| 질문 성격 | 기본 우선순위 |
|---|---:|
| 하드 필터에 필요한 정보 | 100 |
| 안전·필수 지원 | 90 |
| 기간·예산·지역 | 80 |
| 경험 방향 1·2순위를 가르는 정보 | 65 |
| 도시 순위를 가르는 부모 체류 목적 | 50 |
| 설명만 풍부하게 하는 정보 | 20 |

다음 조건이면 질문하지 않는다.

- 이미 구조화 입력 또는 명시 답변으로 확인됨
- 사용자가 이전 빠른 선택으로 확인함
- 답을 알아도 필터·방향·도시·프로그램 결과가 바뀌지 않음

다음 조건이면 확인 질문을 우선한다.

- confidence 0.60~0.84
- 주체가 불분명함
- 명시 답변끼리 충돌함
- 필수 지원 범위가 불명확함
- 답에 따라 상위 후보가 달라짐

confidence 0.85 이상 추론도 완료값이 아니므로 정상 종료 전에 확인한다.

## 9. 추천 알고리즘 명세

### 9.1 전체 순서

```text
1. 활성 사실과 명시 회피·필수조건 확정
2. 부모동반·연령·일정·기간·지원·특별관리·검증된 예산으로 하드 필터
3. 네 가지 경험 방향의 목표 적합도 계산
4. 각 방향 안에서 아이 준비도에 맞는 세부 형식 계산
5. 필수·선호 지원 적합도 계산
6. 아이 프로그램 공급과 부모 체류를 함께 반영한 도시 점수 계산
7. 역할이 다른 도시 최대 3곳 선택
8. 하드 필터를 통과한 실제 프로그램 점수 계산
9. 미확인 정보를 일반 후보와 분리
10. 5점 이내 후보만 Solar가 근거 범위 안에서 비교
11. Solar가 원문 근거와 DB 근거를 분리해 설명
```

모든 계산은 `algorithmVersion`, 사용한 fact revision, DB candidate snapshot과 함께 저장한다. 초기 버전명은 구현 시 `campfit_matching_v3_1`로 시작한다.

### 9.2 하드 필터

다음 조건은 평균 점수로 상쇄하지 않는다.

- 출발 시점 아이 나이가 프로그램 연령 범위에 포함됨
- 프로그램 운영 시기와 가족 출발 가능 기간이 겹침
- 프로그램 가능한 기간과 가족 가능 기간이 겹침
- 부모가 같은 도시에 체류하며 아이가 낮 프로그램으로 참여할 수 있음
- 지역 선호가 `hard`면 해당 지역에 포함됨
- 특별 식사·알레르기·복약·건강 조건을 충족함
- `must`로 지정된 한국어 또는 기타 지원을 충족함
- 검증된 최소 가족 총비용이 사용자 최대예산을 명확히 초과하지 않음
- 프로그램이 `visible=true`, `is_listed=true`이며 DB candidate allowlist에 있음

판정은 세 값으로 한다.

| 상태 | 처리 |
|---|---|
| `pass` | 일반 후보 유지 |
| `fail` | 제외하고 이유 기록 |
| `unknown` | 일반 후보로 통과시키지 않고 “조건 확인 후 살펴볼 후보”로 분리 |

지원이나 특별관리처럼 안전에 직접 영향을 주는 필드가 `unknown`이면 일반 후보가 될 수 없다. 비용 데이터가 불완전하면 예산 초과로 단정하지 않고 `unknown`으로 분리한다.

### 9.3 경험 방향

경험 방향 enum은 네 개뿐이다.

| enum | 사용자 명칭 |
|---|---|
| `schooling` | 학교·스쿨링 경험 |
| `english_intensive` | 영어 집중 경험 |
| `project_topic` | 주제·프로젝트 경험 |
| `culture_activity` | 문화·활동 경험 |

Solar는 목표 신호의 강도를 다음처럼 구조화한다.

| 표현 강도 | 값 |
|---|---:|
| 가장 중요한 목표로 명시 | 100 |
| 명확한 부가 목표 | 70 |
| 가볍게 언급 | 40 |
| 문맥상 추론 | 최대 20 |
| 언급 없음 | 0 |

명시값은 추론값보다 우선한다. 목표별 방향 매칭값은 다음과 같다.

| 부모 목표 | 학교·스쿨링 | 영어 집중 | 주제·프로젝트 | 문화·활동 |
|---|---:|---:|---:|---:|
| 국제학교·현지학교 경험 | 100 | 50 | 50 | 60 |
| 영어 실력 향상 | 70 | 100 | 55 | 40 |
| 자연스러운 영어 노출 | 60 | 80 | 70 | 100 |
| 장기 유학 전 테스트 | 100 | 65 | 45 | 50 |
| 관심 분야 몰입 | 45 | 40 | 100 | 60 |
| 문화와 시야 확장 | 55 | 40 | 60 | 100 |
| 자신감·사회성 | 60 | 55 | 75 | 90 |
| 즐거운 경험 | 40 | 35 | 70 | 100 |

```text
목표 적합도(direction)
= Σ(사용자 목표 강도 × 방향 매칭값)
  / Σ(사용자 목표 강도)
```

목표 강도의 합이 0이면 계산하지 않고 `primary_experience`를 질문한다.

명시 회피·강조 보정은 다음과 같다.

| 사용자 표현 | 학교·스쿨링 | 영어 집중 | 주제·프로젝트 | 문화·활동 |
|---|---:|---:|---:|---:|
| 공부만 하는 프로그램은 싫다 | -20 | -15 | 0 | +10 |
| 실제 정규수업이 꼭 필요하다 | +15 | 0 | 0 | 0 |
| 영어 성과가 최우선이다 | 0 | +15 | 0 | -5 |
| 관심 분야 몰입이 가장 중요하다 | 0 | 0 | +15 | 0 |
| 즐거운 활동이 가장 중요하다 | -5 | -10 | +5 | +15 |

보정 후 결과는 0~100으로 제한한다. 유사한 자유 표현은 Solar가 위 canonical signal로 매핑하되 evidence를 남긴다.

### 9.4 세부 형식과 아이 준비도

학교 방향 점수가 높다고 정규수업을 자동 추천하지 않는다. 세부 형식별 요구도를 1~5로 비교한다.

| 세부 형식 | 영어 요구 | 낮 시간 적응 | 구조화 수업 적응 | 사회 참여 | 관심 분야 |
|---|---:|---:|---:|---:|---:|
| 국제학교 정규수업 | 4 | 3 | 4 | 3 | - |
| 국제학교 방학캠프 | 2 | 2 | 3 | 3 | - |
| 초급 ESL 데이 프로그램 | 1 | 2 | 3 | 2 | - |
| 집중 ESL | 3 | 2 | 4 | 2 | - |
| 체험형 프로젝트 캠프 | 2 | 2 | 2 | 3 | 4 |
| 학습형 프로젝트 캠프 | 3 | 2 | 4 | 3 | 4 |
| 문화·액티비티 데이캠프 | 1 | 2 | 1 | 3 | 2 |

프로그램 요구와 아이 준비도의 차이는 다음처럼 변환한다.

| `요구 단계 - 준비 단계` | 적합도 |
|---|---:|
| 0 이하 | 100 |
| 1 | 75 |
| 2 | 40 |
| 3 이상 | 10 |
| 준비도 또는 요구도 미확인 | 60, confidence 하향 및 확인사항 |

영어 준비도는 첨부 문서의 20/40/60/80/95를 각각 1/2/3/4/5단계로 매핑한다. 낮 시간 적응, 구조화 수업 적응, 사회 참여, 관심 분야 준비도는 명시 답변이 있을 때만 1~5로 변환한다. 없는 축은 0으로 두지 않고 계산에서 제외한 뒤 신뢰도를 낮춘다.

형식 적합도는 해당 세부 형식에 정의된 축만 동일 비중으로 평균한다. 각 경험 방향에서 가장 높은 형식 적합도를 사용한다.

```text
경험 방향 최종점수
= 목표 적합도 70%
  + 해당 방향 내 최고 세부 형식 적합도 30%
```

### 9.5 지원 조건

지원은 세 묶음과 여섯 세부 항목으로 저장한다.

- 아이 직접 지원: 한국어, 영어 초급자, 초기 적응
- 부모 소통: 정기 보고, 문제 발생 시 연락
- 안전·운영: 응급 대응, 특별 식사·알레르기·복약

각 사용자 필요와 프로그램 제공 수준은 0~3으로 정규화한다.

| 수준 | 의미 |
|---:|---|
| 0 | 필요 없음·제공 없음 |
| 1 | 비상 상황에서만 |
| 2 | 정기적 또는 매일 |
| 3 | 상주·지속 대응 |

| 제공 수준과 필요 수준의 차이 | 점수 |
|---|---:|
| 같거나 제공이 더 높음 | 100 |
| 1단계 부족 | 60 |
| 2단계 부족 | 25 |
| 3단계 부족 | 0 |
| 제공 정보 미확인 | 50, 확인 필요 |

중요도 가중치는 `must=3`, `strong=2`, `soft=1`, `none=계산 제외`다.

```text
선호 지원 적합도
= Σ(지원 매칭점수 × 중요도 가중치)
  / Σ(중요도 가중치)
```

`must`는 평균에 의한 상쇄를 허용하지 않는다. 제공 부족은 제외, 제공 미확인은 확인 그룹으로 보낸다. 사용자가 원하지 않은 지원은 보너스가 아니다.

### 9.6 도시 점수

기본 도시 점수는 다음 여섯 축이다.

| 축 | 기본형 | 부모 휴식·여가 중요 | 아이 교육 최우선 | 예산 최우선 |
|---|---:|---:|---:|---:|
| 선호 지역 적합도 | 15 | 10 | 15 | 10 |
| 아이 프로그램 적합성 | 25 | 25 | 35 | 25 |
| 가족 전체 비용 현실성 | 20 | 20 | 20 | 30 |
| 부모 체류 만족도 | 20 | 30 | 10 | 15 |
| 지원·생활 인프라 | 10 | 10 | 10 | 10 |
| 항공·현지 이동 편의 | 10 | 5 | 10 | 10 |

가중치 프리셋은 사용자의 명시적 최우선 목표가 있을 때만 바꾼다. 추론만으로 프리셋을 바꾸지 않는다.

아이 프로그램 적합성의 내부 구성은 다음과 같다.

```text
원하는 경험 방향의 유효 프로그램 공급 50%
아이 나이에 맞는 유효 프로그램 수      20%
희망 시기에 운영되는 유효 프로그램      15%
초급·필요 지원 가능한 프로그램 공급     15%
```

공급 수는 임계치 충족 여부에 사용하고, 프로그램이 많은 도시가 무조건 높은 점수를 받지 않도록 각 항목은 포화 정규화한다. 구현 전 calibration fixture로 포화 기준을 고정한다.

부모 체류 만족도는 사용자가 선택한 축만 비교한다.

- 휴식·웰니스
- 카페·식당
- 쇼핑
- 관광·문화
- 자연·해변
- 원격근무
- 장기체류
- 이동 편의

도시 데이터에 없는 축은 0점으로 처리하지 않고 분모에서 제외한다. 남은 가중치는 합계 100이 되도록 재정규화하며, 누락 축을 결과의 확인사항과 confidence에 기록한다.

### 9.7 가족 전체 비용 현실성

```text
예상 가족 총비용 범위
= 프로그램 가격 옵션
 + 이동 인원 항공료
 + 가족 숙박비
 + 생활비
 + 현지 교통
 + 보험·비자·부대비용
```

| 예산과 예상비용 관계 | 점수 |
|---|---:|
| 예상 최대비용까지 감당 가능 | 100 |
| 예상 범위와 사용자 예산 범위가 겹침 | 80 |
| 예상 최소비용보다 15% 이내 부족 | 60 |
| 15~30% 부족 | 30 |
| 30% 이상 부족 | 0 |
| 필수 비용 데이터 불충분 | 60, 확인 필요 |

하드 제외는 검증된 최소비용이 사용자 최대예산을 명확히 초과하고 데이터 confidence가 정한 임계치 이상일 때만 한다. 현재 `campfit_v2_travel_cost_assumptions`가 0건이므로 MVP 구현 전까지 가족 총비용은 확정 점수가 아니라 “추정·확인 필요”다.

비용 레코드에는 통화, 환율 기준일, 가격 기준일, 시즌, 인원, 기간, 포함·불포함, 출처, confidence를 저장해야 한다.

### 9.8 도시 TOP 3

단순 점수 상위 3개를 반복하지 않고 역할별로 선택한다.

1. 가장 균형 잡힌 도시: 전체 도시 점수가 가장 높음
2. 원래 희망을 가장 잘 살리는 도시: 지역과 교육 목표 적합도가 가장 높음
3. 가족 체류 또는 예산 대안: 부모 체류 또는 비용 현실성이 가장 높음

같은 도시는 중복 선택하지 않는다. 유효 도시가 2곳이면 2곳만, 1곳이면 1곳만 보여주며 수를 채우기 위해 하드 조건을 완화하지 않는다.

### 9.9 프로그램 후보 점수

하드 필터를 통과한 프로그램에만 다음 식을 적용한다.

| 축 | 비중 |
|---|---:|
| 추천 경험 방향과 일치 | 30% |
| 세부 형식·아이 준비도 적합성 | 20% |
| 지원 조건 적합성 | 25% |
| 추천 도시 적합성 | 15% |
| 예산 현실성 | 10% |

`추천 도시 적합성`은 TOP 3 포함 여부가 아니라 이미 계산된 해당 도시의 0~100 점수를 사용해 순환 계산을 피한다.

| 결과 그룹 | 규칙 |
|---|---|
| 우선 살펴볼 프로그램 | 적합도 75 이상, 필수 지원·핵심 비용·일정 확인 |
| 조건 확인 후 살펴볼 프로그램 | 적합도는 높지만 지원·비용·일정 등 핵심 정보 일부 미확인 |
| 함께 비교할 대안 | 적합도 60~74, 일부 선호는 다르지만 하드 조건 충족 |
| 제외 | 하드 조건 불충족, 필수 지원 제공 불가, 또는 적합도 60 미만 |

운영 품질 데이터는 가족 적합도에 평균하지 않는다. 중대한 검증 위험이 확인된 경우 별도의 `recommendation_hold`로 보류할 수 있지만 공개 품질점수는 만들지 않는다.

### 9.10 점수가 비슷할 때 Solar가 개입하는 범위

기본 프로그램 점수 차이가 5점 이내인 후보만 Solar가 전체 맥락으로 순서를 설명·조정할 수 있다.

- 후보 ID는 코드가 제공한 allowlist 안에 있어야 한다.
- 하드 필터, `must`, 안전 보류를 뒤집을 수 없다.
- 명시 사용자 답변과 DB evidence만 근거로 쓴다.
- 조정 전 순위, 조정 후 순위, 근거 fact ID와 evidence ID를 저장한다.
- 근거가 없거나 schema가 맞지 않으면 기본 점수순을 유지한다.

도시 TOP 3의 역할 배정은 코드가 담당하며 Solar가 새로운 도시를 추가하지 않는다.

### 9.11 사용자 점수 표현

내부 계산은 0~100을 사용한다. MVP 화면은 과도한 정밀도를 피하기 위해 정성 등급을 기본으로 한다.

| 내부 점수 | 기본 표시 |
|---|---|
| 80 이상 | 가장 잘 맞는 방향 |
| 70~79 | 함께 검토할 방향 |
| 60~69 | 조건을 조정하면 가능 |
| 60 미만 | 현재는 우선순위가 낮음 |

내부 점수 공개 여부는 최종 승인 항목이다. 공개하더라도 5점 단위 반올림만 허용하며 운영 품질 점수처럼 보이지 않게 라벨링한다.

### 9.12 결과 설명의 근거 규칙

각 설명 문장을 다음 중 하나의 근거와 연결한다.

- `USER_EXPLICIT`: 사용자 명시 답변
- `USER_STRUCTURED`: 기본정보 또는 빠른 선택
- `DB_VERIFIED`: DB fact와 검증일·출처
- `ALGORITHM`: 버전이 있는 계산 결과
- `UNKNOWN`: 신청 전 확인해야 하는 미확인 정보

중요한 주장을 `MODEL_INFERENCE`만으로 설명하지 않는다. 카드에는 “맞는 이유”와 “확인할 점”을 분리하며, 가격·일정·지원이 unknown이면 알려진 범위와 모르는 범위를 함께 쓴다.

### 9.13 첨부 알고리즘의 모호성에 대한 MVP 가정

| 항목 | MVP 가정 | 구현 전 검증 |
|---|---|---|
| 영어 20/40/60/80/95와 요구도 1~5 | 순서대로 1/2/3/4/5 매핑 | 20개 이상 fixture로 경계 검증 |
| 출발·운영 시기 겹침 | 가족 범위와 프로그램 운영 범위의 교집합이 1일 이상이면 가능 | 실제 일정 스키마 확정 필요 |
| 기간 겹침 | 가능한 프로그램 duration 중 하나가 가족 1~4주 범위와 교집합이면 통과 | 고정 시작일·회차 처리 추가 필요 |
| 특별관리 unknown | 일반 후보가 아니라 확인 그룹 | 사용자가 완전 제외를 원하는지 승인 필요 |
| 누락 도시 축 | 0점이 아니라 제외 후 재정규화 | confidence 표시 기준 calibration |
| 도시 공급량 | 포화 정규화, 임계치 판단 중심 | 도시별 프로그램 편중 보정 fixture |
| 프로그램 도시 15% | 해당 도시 원점수 사용 | 순환 참조 회귀 테스트 |
| 최대 10회 | AI 질문 메시지 수 | 합쳐 묻는 질문 UX 테스트 |
| 가족 총비용 | 검증된 입력만 합산, 없으면 확인 필요 | 환율·시즌·유효기간 정책 확정 |

### 10.7 8~12개 핵심 도시 보강 전략

초기 목표는 약 11개 도시를 깊게 완성하는 것이다.

- 기존 심화: Cebu, Saipan, Bangkok, Chiang Mai, Guam 권역, Bali, Auckland
- 추가 우선: Kuala Lumpur, Singapore, Gold Coast, Brisbane
- Mangilao는 확인 후 Guam 권역의 canonical city 또는 하위 location으로 연결

도시를 정식 추천 대상으로 승격하는 데이터 게이트:

1. 공개·검증 프로그램 최소 2개, 권장 3개 이상
2. 연령, 기간, 일정, 현재 가격, 부모동행 조건 95% 이상 채움
3. `must` 지원 항목은 `yes/no/unknown` 100% 기록하고 근거 보유
4. v3 도시 차원 90% 이상 채움
5. 동적 정보가 정한 유효기간 안에 검증됨
6. 네 경험 방향 중 도시가 제공하는 역할이 명확함

프로그램이 1개뿐인 Bali와 Auckland는 도시 설명은 가능하지만 2~3개 프로그램 카드 요건을 충족하지 못한다. 보강 전에는 “대안 부족”을 표시하거나 정식 TOP 3에서 제외한다.

## 11. 결과 계약

결과는 다음 순서를 유지한다.

1. 오늘의 상담 결론
2. 추천 경험 방향 1~2개
3. 역할이 다른 추천 도시 최대 3곳
4. 필요한 지원 조건
5. 현재 조건에서 살펴볼 프로그램 2~3개
6. 최종 선택 전 확인사항
7. 조건 조정 시 가능한 대안

각 프로그램 카드는 이름, 도시, 참여 형식, 연령·기간·가격·지원의 확인 상태, “맞는 이유”, “신청 전 확인할 점”을 분리한다. 카드와 설명은 프로그램 ID·fact ID·알고리즘 버전으로 재현 가능해야 한다.

카드의 표현 금지 예시는 다음과 같다.

- “가장 좋은 프로그램입니다.”
- “한국어 담당자가 보장됩니다.”
- “이 가격이면 충분합니다.”
- “안전합니다.”

대신 다음처럼 쓴다.

> 현재 입력 조건에서는 살펴볼 가치가 있는 후보입니다. 한국어 비상 지원과 실제 일정은 신청 전에 운영기관에 확인해 주세요.

## 15. 보안·개인정보·안전

- Upstage key와 Supabase service-role key는 browser bundle·analytics·error response에 절대 포함하지 않는다.
- raw 상담 원문에는 미성년자와 특별관리 정보가 포함될 수 있으므로 시작 전에 수집 목적·보존기간·삭제 방법을 고지하고 동의를 얻는다.
- `special_care`는 최소한의 구조화 값과 필요한 evidence만 저장한다. 진단명이나 불필요한 상세 건강정보를 유도하지 않는다.
- anonymous session은 서명된 HttpOnly, Secure, SameSite cookie와 server-side ownership 검증으로 재개한다.
- 모든 write 요청은 session ownership, turn version, idempotency key, body 길이, same-origin을 검증한다.
- rate limit은 IP와 session 단위로 적용한다.
- 모델에 DB write 도구·네트워크 도구·service-role credential을 주지 않는다.
- 사용자 발화는 instruction이 아닌 data로 구획한다. 모델 응답은 strict schema, allowed key, candidate ID, evidence로 재검증한다.
- 로그에는 비밀키·전체 URL·raw 민감정보를 남기지 않는다.
- 결과 run에는 입력 revision, 후보 snapshot, 알고리즘 버전, 모델 호출 메타데이터를 저장해 재현한다.

- 금지: DB에 없는 개강일·픽업·한국어 담당자·후기·보장 표현을 생성한다.

## 17. MVP 완료 기준과 시연 시나리오

### 17.1 MVP 완료 기준

- Page 1, 2, 3과 상담 상태가 정의대로 동작한다.
- 기본정보 5개와 대화 필수정보 6개의 11-slot progress가 7.1 산식과 일치한다.
- Solar 응답은 strict schema 검증·fallback·서버 재판정을 거친다.
- 명시 사실·수정·추론·unknown·conflict가 분리 저장된다.
- 하드 필터, 네 방향, 세부 형식, 지원, 도시, 프로그램 점수의 단위 테스트가 있다.
- unknown 데이터가 pass나 fail로 오인되지 않는다.
- 결과에는 1~2 방향, 최대 3 도시, 최대 2~3 프로그램, 확인사항, 조정 대안이 있다.
- 25개 정확도 사례와 오류·재개 사례를 통과한다.
- v1·v2 route, API, 데이터, UI를 변경하지 않는다.
- Upstage·Supabase 비밀값은 server-only이며 raw text가 analytics에 없다.

### 17.2 5분 시연 시나리오

1. 시작 페이지에서 “상담 시작하기”를 선택한다.
2. 만 8세, 여름방학, 2주, 부모 1명·아이 1명, 가족 총예산을 입력한다.
3. “아이는 영어 초급이고 문화 활동 속 영어 자신감이 목표예요. 부모는 카페와 휴식을 원해요.”라고 입력한다.
4. 한국어 지원은 응급시만 필요, 특별관리는 없음, 지역은 유연함을 빠른 선택으로 확인한다.
5. 확인된 정보 접힘 영역과 100% 진척도를 보여준다.
6. 결과에서 문화·활동 방향, 역할이 다른 도시, 검토 프로그램과 가격·지원 확인사항을 보여준다.
7. 지원 정보가 빈 후보가 “조건 확인 후”로 분리된 것을 보여준다.
8. 기간을 3주로 수정해 결과가 재계산되고 수정 이력이 보존되는 것을 보여준다.

## 18. 승인 전 사용자 결정 3개

1. 특별관리 정보가 `unknown`인 후보를 현재 기본안처럼 “조건 확인 후” 그룹으로 둘지, 완전히 제외할지 결정이 필요하다.
2. raw 상담 원문과 특별관리 정보의 보존기간·삭제 방식(기본 제안: 익명 세션 30일, 사용자의 즉시 삭제 가능)을 승인해야 한다.
3. 결과에서 내부 적합도를 숫자 없이 정성 등급으로만 보일지(기본안), 5점 단위 점수를 병기할지 결정해야 한다.
